# Prompt 工程这件事，没你想的那么简单

"Prompt engineering" 听起来像玄学，仿佛只要心诚，模型就会给你正确答案。但做了这么多项目下来，越来越觉得这门手艺其实相当工程化——可以学习、可以量化、可以迭代。

一个好的 prompt 能让 7B 模型干过 70B，一个差的 prompt 能让 GPT-4o 说出胡话。这篇把我用得上手的 prompt 技巧和方法论整理出来， hopefully 对你也有帮助。

## Prompt 的本质

LLM 本质上是条件概率生成器：给定输入，生成最可能的下一个 token。Prompt 就是你给的条件，它决定了模型在哪个概率空间里采样。

所以 prompt 写得好不好，本质是：**你有没有把模型引导到正确的思考路径上**。

## 六个真正管用的原则

### 清晰具体

❌ "写点关于 AI 的东西"

✅ "用 300 字介绍 AI 在医疗影像诊断中的应用，重点讲 CNN 在肺结节检测的效果，读者是医生，少用术语"

模型没法猜你想要什么，你越具体，它越能给你想要的。

### 给上下文

不要假设模型知道你业务的来龙去脉。把背景交代清楚：

```
我们是一家跨境电商，主要市场北美，产品是智能家居。
请根据以下用户评论数据，分析 Top 3 痛点并给出产品改进建议。
```

### 指定角色

"你是一位有 15 年经验的 Python 架构师"这种开头不是装饰，它真的会改变模型输出的风格和专业程度。但别滥用，角色要和任务匹配。

### 明确输出格式

想让模型返回 JSON，光说"请返回 JSON"不够。把 schema 给出来：

```
请以 JSON 格式输出，字段如下：
{
  "summary": "一句话总结",
  "key_points": ["要点1", "要点2"],
  "confidence": 0.95
}
```

更好的做法是用 OpenAI 的 `with_structured_output` 或 Pydantic，让模型在协议层就返回结构化数据。

### 设置约束

"字数 200-300"、"不要用术语"、"不能确定就说不知道"——这些约束是防止模型"放飞自我"的关键。特别是"**不能确定就说不知道**"这一条，能大幅减少幻觉。

### 示例引导

Few-shot 是 prompt 工程里最强大的技巧，没有之一。给 2-5 个精心挑选的例子，效果比写十句指令都好。

## 经典技巧，按需取用

### Zero-shot

直接问。简单问题够用。

### Few-shot

```
评论：这个产品很好用 → 正面
评论：快递太慢了 → 负面
评论：一般般 → 中性
评论：刚收到还没用 →
```

例子越多越准，但边际收益递减。一般 3-5 个最佳。

### Chain-of-Thought (CoT)

让模型"一步步思考"。在数学、逻辑、推理任务上效果立竿见影。

最简单的做法是加一句"请一步步思考"（Zero-shot CoT）。更严谨的做法是给出几个带推理过程的例子（Few-shot CoT）。

```
问题：小明有 5 个苹果，给了小红 2 个，又买了 3 个，现在几个？
请一步步思考。
```

### ReAct

思考与行动交替，主要用于 Agent：

```
[Thought] 我需要查询今天的股价
[Action] get_stock_price("AAPL")
[Observation] 198.5 USD
[Thought] 数据拿到了
[Answer] 苹果今天的股价是 198.5 美元。
```

### Self-Ask

让模型自己给自己提子问题：

```
问题：居里夫人的女儿获得了哪一类诺贝尔奖？

需要回答的子问题：
1. 居里夫人的女儿是谁？
2. 她获得了什么奖？
3. 该奖项属于哪个类别？
```

## 几个结构化方法论

写 prompt 没思路的时候，可以套几个框架。

### RICE

- **R**ole：角色
- **I**nstructions：任务指令
- **C**ontext：上下文
- **E**xamples：示例

### SPAR

- **S**ituation：背景
- **P**roblem：问题
- **A**ction：期望动作
- **R**esponse：响应格式

### CRISPE

Capacity / Request / Insight / Statement / Personality / Experiment

这些框架不是死规矩，只是提醒你别漏掉关键要素。

## 进阶玩法

### Prompt Chaining

把一个复杂任务拆成多个 prompt 串起来。比如：

1. 第一步：提取关键词
2. 第二步：根据关键词检索文档
3. 第三步：基于文档回答问题

好处是每一步可以单独调试、单独缓存。

### Self-Consistency

同样的问题问多次（temperature 调高），然后多数投票。在推理类任务上能显著提高准确率。代价是成本乘 N 倍。

### Meta-Prompting

让 LLM 自己优化 prompt。听起来很酷，实测效果不稳定，但在某些场景下能给出意想不到的改写思路。

## Prompt 在 Agent 里的角色

做 Agent 时 prompt 的重要性被放大了——因为 Agent 的行为模式几乎完全由 system prompt 决定。

一个好的 Agent system prompt 通常包含：

- **角色定义**：你是谁，擅长什么
- **工作流程**：遇到任务怎么拆解
- **工具使用规则**：每个工具什么时候用，什么时候不用
- **输出规范**：格式、风格、语言
- **兜底规则**：不确定时怎么办

工具描述本身就是 prompt。一个工具 docstring 写得是否清晰，直接决定 Agent 会不会用它、用得对不对。

RAG 场景的 prompt 也有讲究。一个我常用的模板：

```
基于以下上下文回答问题。
规则：
1. 优先使用上下文中的信息
2. 如果上下文不足以回答，明确说"根据现有资料无法确定"
3. 回答用 [1]、[2] 标注出处

上下文：
{context}

问题：{question}
```

## 工程化管理

Prompt 一旦上线，就不是"一次写好"的东西，它需要像代码一样管理。

**版本控制**：把 prompt 放到 git 里，每一次改动都有记录。

**模板化**：用 LangChain 的 `ChatPromptTemplate` 或者 LangSmith Hub 管理，避免到处散落字符串。

**评估**：这是最容易被忽略的。准备一个测试集，每次改 prompt 都跑一遍，看指标变化。没有评估的 prompt 优化就是凭感觉。

```python
test_cases = [
    {"input": "...", "expected": "..."},
    # ...
]

for case in test_cases:
    output = prompt_fn(case["input"])
    score = compare(output, case["expected"])
```

## 常见反模式

- **一个 prompt 做所有事**：拆，拆成多个专注的小 prompt
- **描述冗长混乱**：用 Markdown 结构化，该分段分段
- **让模型猜格式**：明确给 schema
- **不给兜底路径**：模型一定要知道"不确定时怎么办"
- **硬编码所有内容**：用变量 + 模板
- **从不评估**：凭感觉优化是最大的坑

## 一些体会

Prompt 工程是 AI 时代的"新编程"，但它和传统编程很不一样——传统编程是和确定性打交道，prompt 工程是和概率打交道。

三条我比较坚信的原则：

**清晰胜过花哨**。与其堆 CoT、few-shot、meta-prompting，不如先把需求说清楚。

**示例胜过描述**。一个好的 example 抵得上十句 instruction。模型更擅长"照葫芦画瓢"，而不是"听话照做"。

**评估胜过直觉**。感觉 prompt 改好了不算，跑个评测集看看数字才算。
